# 项目计划书：共享单车需求预测与调度分析

## 1. 项目基本信息

**项目名称**：共享单车需求预测与调度分析：基于骑行记录与历史天气的多源数据挖掘  
**项目类型**：期末项目选项 A + C，即多源数据融合挖掘与端到端应用系统开发  
**团队规模**：4 人  
**团队成员**：任泓臻（2351458）、虞澍（2352979）、黄彦炜（2353117）、马小龙（2353814）  
**计划周期**：5 周  
**计划交付物**：代码仓库、可运行 Dashboard、实验结果、项目报告、答辩 PPT、项目海报  

## 2. 选题背景与意义

共享单车是城市短途出行的重要组成部分。实际运营中，车辆需求会受到通勤高峰、工作日与周末、天气变化、会员结构、车辆类型和区域功能差异等因素影响，常见问题包括热门站点无车可借、通勤终点车辆堆积、恶劣天气下需求波动明显等。

本项目计划以 Capital Bikeshare 公开骑行记录为主要数据源，并融合 Open-Meteo 历史天气数据，构建一个从数据采集、清洗融合、特征工程、多模型预测到站点调度分析和可视化展示的完整数据挖掘流程。项目不仅关注模型预测精度，也关注预测结果如何转化为可解释的调度建议。

## 3. 研究问题与项目目标

本项目拟围绕以下问题展开：

1. 小时级共享单车需求是否存在稳定的日周期、周周期和季节差异？
2. 天气变量、会员类型和车辆类型是否能增强需求预测效果？
3. 传统机器学习模型、集成树模型和 LSTM 时序模型在该任务中的表现有何差异？
4. 如何基于站点净流入/净流出识别需要补车或清车的重点站点？
5. 如何将预测结果、模型对比和调度建议整合为可交互的 Dashboard？

项目目标包括：

1. 建立可复现的数据处理管道，完成骑行数据与天气数据融合。
2. 构建小时级城市总体需求预测任务，并形成站点级供需不平衡分析。
3. 对比 Seasonal Naive、Ridge、Random Forest、HistGradientBoosting、XGBoost 和 LSTM 等模型。
4. 使用 MAE、RMSE、MAPE 和 R2 进行时间序列切分评估。
5. 实现 Streamlit Dashboard，支持数据概览、模型对比、预测曲线和调度建议展示。

## 4. 数据来源与计划范围

| 数据类型 | 数据来源 | 计划字段 | 主要用途 |
|---|---|---|---|
| 骑行记录 | Capital Bikeshare System Data | 起止时间、起终点站、车辆类型、会员类型、经纬度 | 构建小时级需求和站点级净需求 |
| 历史天气 | Open-Meteo Historical Weather API | 温度、相对湿度、降水、风速 | 分析天气对骑行需求的影响 |
| 时间特征 | 由骑行开始时间派生 | 小时、星期、月份、周末、节假日或周期编码 | 捕捉通勤和周期规律 |

计划使用 2023-2025 三年骑行记录。若本地计算或下载压力较大，可先运行单年或单月烟测；正式实验统一聚合到小时粒度，城市总体需求用于预测任务，Top 站点 pickup、dropoff 和 net demand 用于调度分析、站点聚类和站点级预测。

## 5. 技术路线

项目计划采用以下流程：

| 阶段 | 计划方法 | 计划输出 |
|---|---|---|
| 数据采集 | 下载 Capital Bikeshare 月度 zip，调用 Open-Meteo API | 原始骑行数据、小时级天气表 |
| 数据清洗 | 解析时间戳、过滤异常骑行时长、处理缺失站点 | 清洗后的骑行记录 |
| 数据融合 | 按开始时间聚合到小时，并按 timestamp 合并天气 | hourly_demand.csv |
| 特征工程 | 构造时间、周期、节假日、天气、会员比例、车辆类型比例、滞后和滚动均值特征 | model_features.csv |
| 模型训练 | 按时间顺序切分训练集和测试集，避免时间泄漏 | 模型文件、预测结果 |
| 模型评估 | 使用 MAE、RMSE、MAPE、R2 对比模型表现 | 模型指标表和误差图 |
| 站点增强 | 计算站点净流出/净流入、站点聚类和 Top 20 站点净需求预测 | dispatch_recommendations.csv、station_clusters.csv、station_model_metrics.csv |
| 系统展示 | 使用 Streamlit 和 Plotly 构建交互式 Dashboard | 可运行演示系统 |

## 6. 模型与实验设计

本项目计划设置从简单基线到复杂模型的多层对比：

| 模型类别 | 模型 | 设置目的 |
|---|---|---|
| 时间基线 | Seasonal Naive | 判断模型是否超过简单周期复制策略 |
| 线性模型 | Ridge Regression | 检查基础特征的线性解释能力 |
| 集成树模型 | Random Forest、HistGradientBoosting、XGBoost | 捕捉非线性关系和特征交互 |
| 深度时序模型 | LSTM | 对比序列建模方法在该任务中的适用性 |

实验计划采用时间顺序切分：前 80% 时间段作为训练集，后 20% 时间段作为测试集。该设计可以避免随机切分导致的未来信息泄漏，更接近真实预测场景。

LSTM 部分计划优先检测 GPU 环境；如果 CUDA 可用，则使用 GPU 训练，否则自动退回 CPU。由于该任务包含大量人工构造的表格型时序特征，LSTM 将作为深度学习对照模型，而不是唯一主模型。

## 7. Dashboard 设计

Dashboard 计划包含 5 个页面：

| 页面 | 展示内容 |
|---|---|
| 数据概览 | 数据量、时间范围、天气分布、骑行趋势 |
| 需求预测 | 选择模型，查看真实值与预测值曲线 |
| 模型对比 | 指标表、误差分布、特征重要性 |
| 站点调度 | Top 站点净流出/净流入、补车和清车建议、站点聚类、站点级预测 |
| 项目说明 | 数据来源、技术流程、分工、运行命令 |

系统目标是支持课堂演示：即使不重新训练模型，也能直接读取已有结果文件并展示图表。

## 10. 风险与应对

| 风险 | 可能影响 | 应对策略 |
|---|---|---|
| 数据下载或 API 不稳定 | 无法及时获取全部原始数据 | 缓存原始 zip 和处理后 CSV，支持复用已有数据 |
| 月度文件字段或时间格式不一致 | 清洗流程失败或样本丢失 | 编写字段检查和时间解析测试，必要时按月份兼容处理 |
| 全年数据处理较慢 | 训练和演示耗时过长 | 先完成半年版本，再扩展全年；Dashboard 读取离线结果 |
| LSTM 效果不如集成树模型 | 深度模型贡献不明显 | 将其定位为对照实验，分析任务特征与模型适配性 |
| 现场演示环境波动 | Dashboard 无法稳定启动 | 准备静态 HTML 图表、截图和演示视频作为备份 |
| 团队贡献难以区分 | 个人提交材料不足 | 按模块拆分 commit 和文档章节，保留每个人的文件责任 |

## 11. 验收标准与预期成果

项目完成时应满足以下标准：

1. 数据管道可以从原始骑行数据和天气 API 生成小时级建模表。
2. 至少完成 5 类城市总体模型对比，并输出统一格式的指标和预测文件。
3. 调度分析能够输出站点净流出/净流入排序、站点聚类画像、Top 20 站点预测和补车/清车建议。
4. Streamlit Dashboard 可以在本地启动，并加载全部核心图表。
5. 项目报告能够说明数据、方法、实验设计、模型解释、系统实现和局限性。
6. 每名组员都有明确代码模块、文档章节或实验产出。

预期最终成果包括：可运行代码仓库、处理后数据样例、模型评估表、预测曲线、调度建议 CSV、Streamlit Dashboard、10-20 页项目报告、答辩 PPT 和 A1 项目海报。
