# 项目计划书：共享单车需求预测与调度分析

## 1. 项目基本信息

**项目名称**：共享单车需求预测与调度分析：基于骑行记录与历史天气的多源数据挖掘 

**项目类型**：期末项目选项 C，端到端应用系统开发 

**团队规模**：4 人  

**团队成员**：任泓臻（2351458）、虞澍（2352979）、黄彦炜（2353117）、马小龙（2353814）

## 2. 选题背景与意义

共享单车是城市短途出行的重要组成部分。实际运营中，车辆需求会受到通勤高峰、工作日与周末、天气变化、会员结构、车辆类型和区域功能差异等因素影响，常见问题包括热门站点无车可借、通勤终点车辆堆积、恶劣天气下需求波动明显等。

本项目计划以 Capital Bikeshare 公开骑行记录为主要数据源，并融合 Open-Meteo 历史天气数据，构建一个从数据采集、清洗融合、特征工程、多模型预测到站点调度分析和可视化展示的完整数据挖掘流程。项目不仅关注模型预测精度，也关注预测结果如何转化为可解释的调度建议。

## 3. 研究问题与项目目标

本项目围绕以下问题展开：

1. 小时级共享单车需求是否存在稳定的日周期、周周期和季节差异？
2. 不同天气状态下的日平均需求有何差异，能否作为预测情景调整依据？
3. 传统机器学习模型、集成树模型和 LSTM 时序模型在城市总体需求预测中的表现有何差异？
4. 不同站点在不同时间段内是否存在明显净流入或净流出，如何识别重点补车或清车站点？
5. 如何将城市总体预测、站点级净需求预测、天气情景分析、站点热力图和模型对比整合为可交互 Dashboard？

项目目标包括：

1. 建立可复现的数据处理管道，完成 Capital Bikeshare 骑行数据、Open-Meteo 天气数据和节假日特征融合。
2. 构建小时级城市总体需求预测任务，输出测试集真实值与多模型预测结果。
3. 构建 Top 20 站点级净需求预测任务，支持站点级真实净需求与模型预测对比。
4. 对比 Seasonal Naive、Ridge、Random Forest、HistGradientBoosting、XGBoost 和 LSTM 等城市总体预测模型，并使用 MAE、RMSE、MAPE 和 R2 评估。
5. 基于 pickup、dropoff 和 net demand 形成站点画像、聚类结果、补车/清车建议和地图热力图。
6. 实现 Streamlit Dashboard，支持数据概览、预测窗口选择、天气情景预测、模型对比、站点详情和项目说明展示。

## 4. 数据来源与计划范围

| 数据类型 | 数据来源 | 计划字段 | 主要用途 |
|---|---|---|---|
| 骑行记录 | Capital Bikeshare System Data | 起止时间、起终点站、车辆类型、会员类型、经纬度 | 构建小时级需求和站点级净需求 |
| 历史天气 | Open-Meteo Historical Weather API | 温度、相对湿度、降水、风速 | 分析天气对骑行需求的影响 |
| 节假日与时间特征 | 由骑行开始时间和美国联邦节假日派生 | 小时、星期、月份、周末、节假日、节前/节后、周期编码 | 捕捉通勤、季节和节假日规律 |
| 站点空间信息 | 骑行记录中的起终点经纬度 | 站点名、站点经纬度 | 支持站点地图热力图和站点画像展示 |

项目范围覆盖 2023-2025 三年 Capital Bikeshare 月度骑行记录。系统支持用完整三年数据运行，也支持用单月数据进行快速烟测。正式处理结果统一聚合到小时粒度：城市总体需求使用全系统每小时出发骑行量 `cnt`，站点级分析使用 Top 20 站点的 `pickup_count`、`dropoff_count` 和 `net_demand = pickup - dropoff`。天气分析除小时变量外，还按日汇总不同天气状态下的日平均需求，并将其作为 Dashboard 中天气情景预测的调整依据。

## 5. 技术路线

项目采用以下流程：

| 阶段 | 计划方法 | 计划输出 |
|---|---|---|
| 数据采集 | 下载 Capital Bikeshare 月度 zip，调用 Open-Meteo API | 原始骑行数据、小时级天气表 |
| 数据清洗 | 解析时间戳、过滤异常骑行时长、处理缺失站点 | 清洗后的骑行记录 |
| 数据融合 | 按开始时间聚合到小时，并按 timestamp 合并天气；同时生成 Top 站点小时级 pickup/dropoff/net demand | hourly_demand.csv、station_hourly.csv、weather_hourly.csv |
| 特征工程 | 构造时间、周期、节假日、天气、会员比例、车辆类型比例、滞后和滚动均值特征 | model_features.csv |
| 天气情景分析 | 将每日天气归类为常规天气、降水、高温、低温或大风，并计算各类日平均需求相对常规天气的倍数 | Dashboard 天气日均需求图、天气情景系数 |
| 城市模型训练 | 按时间顺序切分训练集和测试集，避免时间泄漏 | metrics.json、predictions.csv、模型文件 |
| 模型评估 | 使用 MAE、RMSE、MAPE、R2 对比模型表现 | 模型指标表和误差图 |
| 站点增强 | 计算站点净流出/净流入、站点聚类、Top 20 站点净需求预测和补车/清车建议 | dispatch_recommendations.csv、station_clusters.csv、station_model_metrics.csv、station_predictions.csv |
| 系统展示 | 使用 Streamlit、Plotly 和 OpenStreetMap 底图构建交互式 Dashboard | 可运行演示系统 |

## 6. 模型与实验设计

城市总体需求预测设置从简单基线到复杂模型的多层对比：

| 模型类别 | 模型 | 设置目的 |
|---|---|---|
| 时间基线 | Seasonal Naive | 判断模型是否超过简单周期复制策略 |
| 线性模型 | Ridge Regression | 检查基础特征的线性解释能力 |
| 集成树模型 | Random Forest、HistGradientBoosting、XGBoost | 捕捉非线性关系和特征交互 |
| 深度时序模型 | LSTM | 对比序列建模方法在该任务中的适用性 |

实验采用时间顺序切分：前 80% 时间段作为训练集，后 20% 时间段作为测试集。该设计可以避免随机切分导致的未来信息泄漏，更接近真实预测场景。城市总体预测结果写入 `models/predictions.csv`，其中每一行表示某一小时全系统出发骑行量的真实值和各模型预测值。

LSTM 部分计划优先检测 GPU 环境；如果 CUDA 可用，则使用 GPU 训练，否则自动退回 CPU。由于该任务包含大量人工构造的表格型时序特征，LSTM 将作为深度学习对照模型，而不是唯一主模型。

站点级净需求预测单独面向 Top 20 高流量站点建模，目标变量为 `net_demand = pickup_count - dropoff_count`。站点级模型当前包括 Ridge、Random Forest、HistGradientBoosting 和 XGBoost 四类模型，输出 `models/station_predictions.csv` 和 `reports/tables/station_model_metrics.csv`。该任务用于支持站点详情页中的“真实净需求 vs 模型预测净需求”对比，并允许用户选择站点、模型、预测起点和预测周期；选择 `None` 时只展示真实净需求曲线。

天气情景预测基于历史数据中不同天气状态的日平均需求与常规天气日平均需求之比，作为站点预测动画中的需求强度调整系数。

## 7. Dashboard 设计

Dashboard 包含 5 个页面：

| 页面 | 展示内容 |
|---|---|
| 数据概览 | 总骑行量、小时样本、每日骑行总量、小时平均需求、需求与天气变量相关性、节假日/星期/月度日平均需求、不同天气的日平均需求 |
| 需求预测 | 城市总体需求预测曲线；支持选择模型、开始日期和测试天数；展示预测误差分布；提供站点预测动画和天气情景调整 |
| 模型对比 | MAE、RMSE、MAPE、R2 指标表；误差指标柱状图；LSTM 训练信息和特征解释说明 |
| 站点详情 | 调度建议表、站点聚类分布与画像、站点历史热力图、站点级真实净需求与模型预测对比 |
| 项目说明 | 数据来源、技术流程、运行命令和模型指标 JSON |

系统目标是支持课堂演示：即使不重新训练模型，也能直接读取已有结果文件并展示图表。Dashboard 中的时间控件支持选择预测起点、测试天数和预测周期；站点地图使用 OpenStreetMap 底图，红色表示站点净流入更多，蓝色表示站点净流出更多。

## 10. 风险与应对

| 风险 | 可能影响 | 应对策略 |
|---|---|---|
| 数据下载或 API 不稳定 | 无法及时获取全部原始数据 | 缓存原始 zip 和处理后 CSV，支持复用已有数据 |
| 月度文件字段或时间格式不一致 | 清洗流程失败或样本丢失 | 编写字段检查和时间解析测试，必要时按月份兼容处理 |
| 全年数据处理较慢 | 训练和演示耗时过长 | 先完成半年版本，再扩展全年；Dashboard 读取离线结果 |
| LSTM 效果不如集成树模型 | 深度模型贡献不明显 | 将其定位为对照实验，分析任务特征与模型适配性 |
| 现场演示环境波动 | Dashboard 无法稳定启动 | 准备静态 HTML 图表、截图和演示视频作为备份 |
| 团队贡献难以区分 | 个人提交材料不足 | 按模块拆分 commit 和文档章节，保留每个人的文件责任 |
